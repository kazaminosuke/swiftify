# Swiftify native playback

The native branch starts at the fork's `main` commit `21e6d0e`. The
previous Data API, OAuth, desktop-window and packaging drafts (#1–#4) remain
available for review. The playback branch is independent of their browser
handoff and does not initialize a Spotify or Google account.

## Engine milestone

`native-audio` is an independent Rust crate. It moves the CPAL stereo device
adapter into shared code and keeps the original Spotify output caller through
a wrapper. The standalone player opens a supplied audio file using Rodio's
Symphonia decoders and converts to the device sample rate and stereo on a
decoder thread. A bounded PCM queue separates that thread from the callback.
The callback uses try-locks and outputs silence during contention or underrun.
Pause, resume, seek, stop and volume use native playback controls. Seek
prepares a replacement decoder before switching the active input.

Build and run from the repository root:

```sh
cargo run --locked --manifest-path native-audio/Cargo.toml --example play-file -- /path/to/audio.wav
```

The clock advances on PCM frames submitted to the output. It excludes silence
generated by an underrun. The snapshot also exposes an optional audible
position and output latency estimate, based on CPAL timestamps and a bounded
history of submitted PCM. On pause, it freezes the estimate and on resume it
reschedules the remaining estimated output. A successful load, seek or stop
changes the timeline revision. The engine can remain in `Draining` until the
last PCM buffer is estimated to have finished. The estimate may omit
downstream hardware latency, and an abrupt seek does not control media that
the operating system already buffered.

## Service boundary and integration

The current playable input is a local file. Future network adapters will
supply media bytes, content identity, format and seek capabilities to the
engine. They will own authentication, endpoint policy, retry and
cancellation. The local decoder currently reads an iterator of samples.
Before queue integration, the network playback path needs to distinguish
decode failure, temporary lack of bytes and natural EOF. Metadata credentials
from the earlier Data API draft grant access to metadata only.

The C++ bridge should call native control operations on a worker thread.
QML will consume a coherent snapshot with the playback phase and positions.
For synced lyrics, the C++ bridge still needs to timestamp snapshots for QML
against a shared monotonic clock and expose playback rate. The audible
estimate also needs source-frame accounting once tempo or other latency-bearing
DSP is added. Advance cues from the current revision only and freeze them
during explicit pauses and playback stalls.

The existing equalizer, spectrum and tempo DSP remain useful project code.
Before sharing their processing with this engine, parameterize the DSP with
the negotiated sample rate and format. Account for DSP buffering and tempo
changes explicitly in the media timeline.

Service permission and open-source licensing need separate review. The
[source comparison](youtube-music-client-comparison.md) records the named
open-source implementations, their licenses and service constraints.

## Local verification

- Six Rust unit tests verify render-to-clock accounting, non-blocking
  callback behavior, final-buffer timing, frame precision, underrun clock
  behavior and the pause/resume boundary.
- The integration test played a generated mono WAV through the Linux ALSA
  null device, checked a paused seek, preserved state on a corrupt-file
  error, and verified progress, drain, stop and timeline revisions.
- The standalone player emitted non-zero PCM to the ALSA file device for
  generated WAV and AAC/MP4 samples. The bundled decoder rejected the
  generated Opus/WebM sample.
- The existing Spotify core's release suite passed locally with 74 tests and
  one opt-in benchmark ignored. The engine passed Clippy with warnings denied.
- Linux and Windows CI passed the native engine, existing output and C ABI
  tests. Linux CI also ran the ALSA device test. Physical audio output on
  Windows and Linux remains unverified.
  [Linux and Windows CI](https://github.com/kazaminosuke/swiftify/actions/runs/44709909645)
